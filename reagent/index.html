01 — TL;DR

The shortest possible version.

Reagent is Spellbook's internal program for making every team and every internal agent faster, by guaranteeing the context they need to do their work is available, accurate, and useful. Reagent treats context as an ingredient: a reagent in a chemistry experiment, an input with a known source, freshness, and purity, without which the work fails. The name is a deliberate pun: in this project, an agent is only as good as its re-agents.

Reagent is operationalized as a growing, version-controlled library of evals — small executable tests that pair a real business question with the canonical answer and the context the agent should have consulted to produce it. When an eval fails, Reagent classifies why: missing context, stale or incorrect context, or a reasoning error inside the agent. The first two open tickets against the source team. Over time, that ticket stream becomes the de-facto roadmap for the company's data bus.

The implementing team's job is to ship the eval format, the runtime that executes evals against real agents, the web authoring tool that lets any team (technical or not) contribute their own, and the dashboard that turns failures into a prioritized backlog. The pilot spans Sales and Finance over one quarter.

02 — Why this matters

Today, knowing what we know is paid for over and over.

Every decision at Spellbook gets faster when the person, or the agent, making it has the right context within reach. Today that context is fragmented across warehouses, Notion, Drive, Slack, email, ticketing systems, and people's heads. Even where it exists, it is often stale, ambiguously named, or in a format that can't be consumed by an agent without bespoke wiring.

Two consequences follow:

  1. Agents look smart in demos and unreliable in practice. They fail not because the model is weak but because the context they pull is missing, stale, or wrong.
  2. The cost of "knowing what we know" is paid over and over. A new hire, a manager preparing a board update, and an agent answering a customer all repeat the same archaeology because nothing surfaces the canonical answer.
The bet

If we make the gaps in our context legible, ranked by business impact, and executable as repeatable tests, every team's data and documentation hygiene improves fast — because shipping an agent, a feature, or a dashboard requires passing the relevant evals the way shipping code requires passing tests. Reagent becomes CI for context.

03 — Vocabulary

Plain names for plain things, with one piece of poetry.

We use one evocative name — Reagent — because the agent / re-agent pun is the whole conceptual frame. Everything else is called what it is.

Reagent
The project, and the unit of context. A reagent is anything an agent or person needs to produce a correct answer: a warehouse table, a Notion page, a Slack thread, a decision record, a person's tribal knowledge, an API.
Eval
One executable test. A question, the canonical answer, the reagents it should use, and the assertions that prove correctness. was: incantation
Library
The full set of evals, version-controlled in Git, organized by department. Two tiers: team-local (anyone can add, runs immediately) and canonical (reviewed, contributes to company rollups). was: Grimoire
Agent
The system under test. Could be a production internal agent, a new agent being shipped, or a thin harness wrapping the same tools and prompts. was: Caster
Oracle
The canonical procedure for producing the true answer to an eval's question. Usually a SQL query, a Python snippet, a pinned doc excerpt, or a human-attested fact with an expiry date.
Assertion
A check applied to the agent's answer or trace. Numeric equality / tolerance, rubric grading, "must have used this reagent", citation present, freshness within bounds.
Promotion
Moving an eval from team-local to canonical. Requires PR review by the department owner plus a Reagent platform reviewer. was: inscription
Context gap
A structured ticket auto-filed against the source team when an eval fails due to missing or stale context. The ticket stream is the data bus build-out backlog.
04 — Primary users

Two audiences, both first-class.

1. Agent and tool builders

Engineers and PMs building internal agents at Spellbook. They use Reagent like CI: before shipping, the relevant slice of the Library must pass. Failures point them precisely at whether to fix the agent, request a new connector, or escalate a data hygiene issue to the source team.

2. Department owners and operators

Heads of Sales, Finance, People, Legal, Product. They author the evals that matter to their domain. They are the source of truth for what questions are worth answering reliably, and they are the primary consumers of the per-department health dashboard.

Mental model

Agent builders are users of the Library. Department owners are authors of it. The product must delight both.

05 — Success metrics

What "this is working" looks like.

North star

⤵
Median time from question → trusted answer, measured weekly across a fixed basket of representative business questions. Baseline is captured in week 1 of the pilot.

Leading indicators

  • Library pass rate by department and overall, trended weekly.
  • Context-gap closure velocity. For each failing eval that opens a context-gap ticket, time-to-close.
  • Coverage. Number of canonical evals per department, weighted by question importance (P0/P1/P2 set by the department owner).
  • Adoption. Number of distinct authors contributing evals per month; number of internal agents gated on Library passes.

Counter-metrics

Watched so we don't game ourselves:

  • Pass rate climbing while real questions still take days to answer (signals the Library is testing the wrong things).
  • Author counts climbing while eval quality drops (signals the review bar is too loose).
06 — Core concepts

The data model in one page.

The eval

An eval is a structured, versioned object with:

  • Identity: id, title, department, owner, version, tier.
  • Question: the natural-language question, phrased the way an employee would actually ask.
  • Parameters: optional named variables ({quarter}, {region}) that let one eval cover a family of real questions.
  • Reagents: the declared context inputs the question should use. Each has a type (table, doc, slack_thread, tribal, api), a locator, and a freshness expectation.
  • Oracle: the canonical way of producing the true answer. Becomes the ground-truth at run time.
  • Assertions: the checks applied to the agent's output and trace.
  • Cadence: when this eval runs (on-demand, nightly, on data change, on agent release).

Failure taxonomy

Every failed eval is classified into exactly one of three buckets. This classification is the engine that turns Reagent into a real-world remediation backlog.

Missing
Missing reagent

The agent couldn't find or access required context. Connector down, doc not indexed, table not visible to the role.

Stale
Stale or incorrect reagent

The agent found context, but it disagrees with the oracle. Stale doc, schema drift, two systems-of-record disagree, ambiguous naming.

Reasoning
Reasoning error

Reagents were present, fresh, and unambiguous; the agent's reasoning or output was simply wrong. A model problem, not a context problem.

Missing and stale failures auto-open a context-gap ticket in the source team's tracker, with the eval id, the specific reagent that failed, and a suggested remediation. Reasoning failures are routed to the agent owner.

The Library

Git-backed monorepo of YAML eval files, organized by team-local/<department>/ and canonical/<department>/. A thin metadata index in Postgres powers the dashboard ("show me every Sales eval failing this week"). The same eval file is the source of truth whether it was authored in the web tool, via natural language, or hand-written by an engineer.

07 — What an eval looks like

The canonical format is YAML.

Most evals will not use every field. Sensible defaults keep the average eval under thirty lines of YAML. Here is the full shape, annotated. 

eval.yaml — full shapeid: sales.cohort_revenue.quarterly
title: "Quarterly revenue by customer cohort"
department: sales
owner: head-of-sales@spellbook.legal
version: 3
tier: canonical            # or team-local
importance: P0                # P0 | P1 | P2

question: |
  Find the {metric} by customer cohort for {quarter}.

parameters:
  metric:   { default: revenue, allowed: [revenue, gross_margin] }
  quarter:  { default: current, type: quarter_ref }

reagents:
  - id: warehouse.fct_invoice
    type: table
    locator: warehouse://analytics/fct_invoice
    freshness: live
    must_use: true
  - id: cohort_definition_doc
    type: doc
    locator: notion://sales/cohort-definitions
    freshness: "<=30d"
    must_use: false

oracle:
  kind: sql
  source: warehouse
  query: |
    select c.cohort_quarter, sum(i.amount_usd) as revenue
    from analytics.fct_invoice i
    join analytics.dim_customer c on c.id = i.customer_id
    where i.fiscal_quarter = :quarter
    group by 1;

assertions:
  - { kind: numeric_table_match, on: revenue, rtol: 0.005 }
  - { kind: trace_must_include, reagents: [warehouse.fct_invoice] }
  - { kind: citation_present }

cadence:
  triggers: [on_demand, nightly, on_schema_change, on_agent_release]

Assertion kinds at v1

  • numeric_equals / numeric_within — absolute or relative tolerance.
  • numeric_table_match — compare two tables row-by-row with tolerance.
  • string_contains / string_matches_regex — for exact-phrase or pattern checks.
  • rubric — LLM-graded against a stated rubric. Judge model and rubric text are both versioned.
  • trace_must_include / trace_must_not_include — which reagents were actually consulted.
  • citation_present — agent must cite at least one reagent with a resolvable locator.
  • freshness_within — source freshness check, independent of the answer.

Oracle kinds at v1

  • sql — parameterized warehouse query.
  • python — short snippet with allow-listed imports, deterministic.
  • pinned_doc — a frozen excerpt of a Notion/Drive doc, used when ground truth is qualitative.
  • human_attested — a human-confirmed answer with an expiration date. The runtime warns the owner as expiry nears.
08 — Example evals, simplest first

From a one-line check to a real Sales rollup.

The implementing team should ship the format such that the average eval is short. These four examples ladder from "the simplest thing that can possibly be useful" up to the worked Sales example.

Example 1 — A single number from one table

The simplest possible eval. One reagent, one numeric assertion, one oracle SQL query.

headcount.current — simplestid: people.headcount.current
title: "What is the current headcount?"
department: people
owner: head-of-people@spellbook.legal
importance: P1

question: "How many employees does Spellbook have today?"

reagents:
  - { id: hris.employees, type: table, locator: warehouse://hris.dim_employee, freshness: live }

oracle:
  kind: sql
  query: "select count(*) from hris.dim_employee where employment_status = 'active'"

assertions:
  - { kind: numeric_equals }
  - { kind: trace_must_include, reagents: [hris.employees] }

Example 2 — A single fact from one document

A policy lookup. Pinned doc as oracle, rubric assertion, must-cite.

parental_leave.us — doc lookupid: people.parental_leave.us
title: "US parental leave policy"
department: people
owner: head-of-people@spellbook.legal
importance: P0

question: "What is the US parental leave policy: weeks of leave and pay continuation?"

reagents:
  - { id: policy_doc, type: doc, locator: notion://people/policies/parental-leave-us, freshness: "<=180d" }

oracle:
  kind: pinned_doc
  source: notion://people/policies/parental-leave-us
  pinned_at: 2026-04-01
  expires_at: 2026-10-01

assertions:
  - kind: rubric
    rubric: "Answer must state weeks of leave for both birthing and non-birthing parents, and pay continuation %."
  - { kind: citation_present }

Example 3 — A boolean check on a process

Useful for compliance and ops questions. Combines a structured assertion with a freshness check.

backup.policy_compliance — booleanid: engineering.backups.production_compliant
title: "Are production backups within policy?"
department: engineering
importance: P0

question: "Is our production database backed up within the last 24 hours per the retention policy?"

reagents:
  - { id: backup_log, type: table, locator: warehouse://ops.backup_runs, freshness: live }

oracle:
  kind: sql
  query: "select max(completed_at) > now() - interval '24 hours' as ok from ops.backup_runs where target = 'prod_primary'"

assertions:
  - { kind: numeric_equals }
  - { kind: freshness_within, reagent: backup_log, threshold: "24h" }

Example 4 — The user's seed question

"Find the sales by customer cohort for this quarter." This is the worked example shown in §07 above. It combines structured numeric assertions, trace assertions, and a multi-reagent dependency. It's the shape that most Sales and Finance evals will take.

A pattern worth noticing

The simplest evals are one reagent + one oracle + one assertion. They are cheap to author, cheap to run, and they collectively make the Library wide rather than deep at the start. Depth comes later, as failures expose what the dashboard needs to distinguish.

Two lanes, both required.

→
Fast lane
+
Full lane
→
Grader
→
Dashboard
// fast lane = reagent reachability + oracle health · full lane = end-to-end against a real agent

Fast lane (always on)

For each eval, the runner exercises only the reagent-reachability and oracle-execution portion: can the agent access the declared reagents? does the oracle still produce a well-shaped answer? have any freshness expectations been violated? Runs in seconds, no model call to the agent. Catches the bulk of context-bus regressions — connector outages, renamed tables, stale docs — which is most of what we care about.

Full lane (scheduled subset and on-demand)

For all P0 evals plus a sampled tail, the runner sends the parameterized question to a real agent with full tool access, captures the response and the trace, and runs the full assertion suite including rubric grading. This is where reasoning-error failures surface and where the agent's real performance is measured.

A single eval's pass/fail is composite: fast-lane health plus the most recent full-lane result. The dashboard exposes both, so a P0 with a recent fast-lane regression is visible immediately without waiting for the next full-lane window.

10 — The authoring tool

A web tool that meets people where they are.

YAML and Git make the Library durable, auditable, and toolable. They also exclude the vast majority of the people whose evals we want — Sales leaders, Finance ops, People partners. The authoring tool's whole purpose is to remove that exclusion without losing the canonical YAML as source of truth.

The tool offers three authoring modes, all of which compile to identical YAML and submit a pull request under the hood.

Mode 1 — Ask in plain English (the default)

A single text box and a "compose this eval" button. The author types something like: "I want to verify that anyone asking about US parental leave policy gets the right number of weeks and the right pay continuation, citing the Notion policy doc."

An LLM that has been prompted with the full Reagent format and the company's available reagents (warehouse schema, indexed docs, connected systems) drafts a complete eval — question, parameters, candidate reagents, oracle scaffold, assertions. The author sees the drafted YAML and a human-readable summary side-by-side, edits either, and submits. Behind the scenes the LLM is given:

  • The eval spec and a curated set of high-quality example evals.
  • The author's department and recently viewed reagents, to ground suggestions.
  • A retrievable index of every reagent locator the company has ever declared, so it can suggest specific tables, docs, and channels rather than placeholders.
  • An evaluator pass that lints the draft before showing it to the author (catches missing oracle, ambiguous question, undeclared reagent, etc.).

This mode is the path of least resistance and is intended to produce the bulk of contributed evals.

Mode 2 — Visual builder (for the structured-minded)

A step-by-step form: name your eval → write the question → add reagents (autocomplete against connected systems) → choose an oracle (SQL helper, doc picker, Python sandbox, or human-attested) → pick assertions from a typed menu → set cadence and importance.

Every field has inline help that explains what it does and shows a one-line example. The reagent picker is connector-aware — pick "Warehouse table" and you get a typeahead over your warehouse schema; pick "Notion doc" and you get the document tree. The form previews the compiled YAML in real time. This mode is best for repeatable patterns (most quarterly metrics, most policy lookups) and for users who want to feel in control of each field.

Mode 3 — YAML / SDK (for engineers)

Engineers can author directly in YAML or via a Python/TS SDK that wraps the same schema and gives them fixtures, parameterization helpers, and unit-test style assertions. The web tool's outputs are byte-for-byte compatible with hand-authored YAML. Engineers can also import an existing eval into the web tool, edit it visually, and round-trip without churn.

Record-and-replay: a fourth on-ramp

Independent of the three modes above, every internal agent that integrates Reagent's tracing emits a candidate eval for any conversation that ended with a user thumbs-down + correction. The candidate is pre-populated with the user's original question, the agent's trace, and the user's correction as a scaffolded oracle. The author opens the candidate in the web tool — usually in Mode 2 — finishes it in a few clicks, and submits. This loop turns daily friction into Library growth without anyone deliberately sitting down to "write evals".

The Git relationship

The tool is a thin layer on top of Git. Every submitted eval, regardless of authoring mode, opens a pull request against the Library monorepo. Team-local evals auto-merge after CI passes (YAML parses, oracle executes, no PII detected by the linter). Canonical evals require human review per §11. Authors see PR status in the web tool; the tool is the primary surface for non-engineers but it never hides the underlying mechanism from anyone who wants to look.

Why this matters more than the runtime

The hardest problem in Reagent is not the executor — it's sustaining contribution from departments that have never written an eval in their lives. If the authoring tool is mediocre, Reagent dies as a platform-team side project. If it's excellent, every department head will want their Library to grow.

Why this is the goal, not the dashboard

A dashboard is something you have to remember to open. #reagent-sales is something that meets people in the channel where work already happens. The dashboard exists, but the lived experience of Reagent is in Slack — verified answers on demand, proactive health summaries, and failures that route themselves to the right team without anyone playing detective.

Surface checklist for the implementing agent

  • Per-department channel (#reagent-sales, #reagent-finance, …) with daily health post and failure alerts.
  • One company-wide channel (#reagent) for canonical-eval promotions, weekly cross-department rollups, and platform announcements.
  • @reagent mention works in any channel: "@reagent verify X" returns a verified answer card with the eval id, importance, last-run time, and reagents consulted.

12 — Governance & promotion

Two tiers, two bars.

Team-local evals

Live in team-local/<department>/. Anyone in the department, or any agent builder targeting it, can add one. Auto-merges after CI passes. Runs immediately. Contributes to the department's pass rate but not to the company-wide rollup. Bar: it must parse, the oracle must execute, the author must be a known identity, the LLM linter must not flag it for duplication or quality issues.

Canonical evals

Live in canonical/<department>/. Promoted via pull request, reviewed by the department owner and a Reagent platform reviewer. The review checklist:

  • Question is real (someone has actually asked this) and clearly worded.
  • Oracle is reproducible and not over-fit to one moment in time.
  • Reagents are correctly declared and resolvable.
  • Assertions are tight enough to catch real regressions, loose enough not to flake.
  • Importance (P0/P1/P2) is set appropriately.

An LLM linter pre-screens PRs and surfaces issues — duplicate, ambiguous question, missing freshness expectation, suspected PII — before human review.

13 — Cadence & triggers

When evals run.

  • Canonical P0. On-demand, nightly full-lane, fast-lane on every data/connector change, blocking on agent release.
  • Canonical P1/P2. On-demand, weekly full-lane, fast-lane on data/connector change.
  • Team-local. On-demand, fast-lane on data/connector change, full-lane only on explicit author run.

"Blocking on agent release" means shipping a new internal agent that claims domain coverage requires the relevant slice of the canonical Library to pass. This is the lever that makes Reagent CI for context. It is held until Q2 (see §14).

14 — Pilot scope

Two departments, one quarter, the whole loop.

The pilot is an end-to-end thin slice. The goal is not breadth — it is proving the whole loop works for two real departments, and producing enough value that other departments ask to join.

Pilot departments: Sales and Finance

Chosen because the questions are high-leverage and executive-visible, the data is largely structured and oracle-able, and early failures will surface real, fixable context-bus issues that earn the project credibility.

Pilot deliverables (12 weeks)

  • Runner, Grader, Oracle service, Library store, basic Dashboard — all minimally functional.
  • Web authoring tool with Modes 1 and 2 live (Mode 3 / SDK can be CLI-only at MVP).
  • Record-and-replay candidate stream from at least one internal agent.
  • ~25 canonical evals per pilot department (50 total), each P0 or P1.
  • Context-gap tracker integration with one ticketing system that Sales and Finance already use.
  • Weekly trended report to the exec team: pass rate, top failures, time-to-trusted-answer.

Out of pilot

Other departments, the LLM linter, the SDK, advanced assertion kinds, and the agent-release gate. All introduced in Q2.

16 — Out of scope

What Reagent is not.

  • Building the agents themselves. Reagent evaluates agents; it does not build them. Existing internal agents are the initial subjects.
  • Remediating upstream data sources. Reagent identifies gaps and files tickets; the source team owns the fix.
  • External / customer-facing agents. Internal use only at v1.
  • Permissions, PII, and compliance redesign. Reagent inherits existing access controls and respects them in the runner. Must be designed for, not re-architected.
  • Real-time / sub-second evaluation. Triggers are event-driven but not streaming.
17 — Dependencies & risks

What we depend on, and what could break.

Dependencies

  • Read-only warehouse access for the Oracle service with a stable service account.
  • Read access to Notion, Drive, Slack, and the chosen ticketing system via existing connectors.
  • A versioned, callable interface to each pilot department's internal agent.
  • A Git repo with PR review enabled and CI hooks for the Library store.

Risks

  • Flaky live-oracle queries. Mitigation: tolerances, retry policies, an explicit flaky-review queue.
  • Authoring bottleneck. If only the platform team writes evals, Reagent dies as a side project. Mitigation: invest disproportionately in the web authoring tool, especially Mode 1; staff a part-time Reagent fellow in each pilot department for the first six weeks.
  • Vanity pass-rate. Teams optimize for green by writing trivial evals. Mitigation: importance weighting set by the department owner, and the time-to-trusted-answer counter-metric.
  • Permission drift between agent and oracle. The oracle may see data the agent cannot. Mitigation: explicit permission_context field per eval and a periodic audit.
  • LLM judge instability. Rubric-graded assertions drift as the judge updates. Mitigation: pinned judge model; rubric assertions report a rolling stability score and flag when it degrades.
18 — Open questions

Decisions deferred to design review.

  1. Agent invocation interface. Call existing internal agents over a stable HTTP/SDK boundary, or run a thin Reagent harness wrapping the same tools? Recommended: the harness, for trace fidelity. More upfront work.
  2. Trace format. OpenTelemetry-style spans for reagent consultation, or a Reagent-native schema?
  3. Rubric judge model. Which model is the pinned judge? How is its version surfaced in failure records?
  4. Library repo organization. Monorepo with team-local/ and canonical/ siblings vs. one repo per department. Recommended: monorepo, with CODEOWNERS rigor.
  5. Identity model. How does an author identity map across the web tool, the YAML owner field, and the source-control commit author?
  6. Cost ceiling. Budget per nightly full-lane run. Sampling policy if cost dominates.
19 — Definition of done

v1 is done when…

  1. A live, scheduled Reagent runtime executes both lanes against real agents for Sales and Finance.
  2. The Library has ~50 canonical evals across the two pilot departments, authored across all three modes.
  3. The dashboard shows per-department pass rate, top failures, open context-gap tickets, and the trended north-star metric.
  4. A documented, repeatable onboarding flow lets us add a third department in under four weeks.
  5. A retrospective with both pilot department owners would have them sign their names as customers, not internal beta-testers.

If any of those five are missing, v1 is not yet done.
